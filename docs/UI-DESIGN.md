# dsht UI 设计报告

> 用途：交给另一位设计者（人或 AI）评审。
> 读这份文档的人**看不到实际界面**，所以下面尽量把布局、颜色、状态都用文字/示意图描述清楚。

---

## 一、这是什么

**dsht** 是一个 **dsh** 的终端界面（TUI）。

- **dsh** = DeepSeek Harness，一个 AI agent 框架。它有后端（agent、工具、会话）和一套官方 HTTP + WebSocket API。
- dsh 官方只有**浏览器界面**。dsht 是**另一个前端**：跑在终端里，通过官方 API 连同一个后端。
- 项目红线：**dsht 不修改 dsh 任何文件**，只是一个「另一种浏览器」。

**目标用户**：本项目的主人是一位**医学生（非程序员）**。他懂概念、不写代码。设计上要求：
- 不需要记命令/快捷键（所以有菜单）
- 中文优先（界面文案全中文）
- 长时间看不能累

**核心交互模型：游戏式暂停菜单。** 用户自己的描述：

> 主屏幕就完全是输入和输出。按 `/` 可以调出命令。按 `Esc` 可以调出一个面板，里面有会话选择、设置、模型选择、退出等菜单。

（说明：`Esc` 菜单是**下一步**要做的，目前 `Esc` 还没接管。）

## 二、设计约束（**很重要**，决定了什么能做、什么做不了）

这一节请先读，否则会觉得很多设计"为什么不做成更好的样子"。

| 约束 | 后果 |
|---|---|
| **终端是字符网格** | 没有像素布局、没有圆角自由、没有平滑动画。所有位置都得按"第几行第几列"算 |
| **颜色只有 16 个基础色**，且**由用户的终端主题决定** | 我们写 `green`，在用户机器上可能是任何绿。不能用真彩色（`#7aa2f7`），因为浅色背景下会看不清 |
| **字符宽度不一致** | 中文占 **2 列**，ASCII 占 1 列，emoji 和部分符号宽度**不确定**。所有对齐、折行、截断都必须自己算显示宽度 |
| **按键上报不一致** | 很多终端**根本不上报** `Shift`/`Ctrl` 修饰键。实测数据见 `docs/TERMINAL-KEYS.md`。比如：`Shift+Enter` 和 `Enter` 送出的字节**完全相同**，无法区分 |
| **中文输入法只认"终端真光标"** | 不能自己画一个光标符号（输入法的拼音会跑到别处）。必须把真光标搬到输入位置 |
| **不能改后端** | 只能通过官方 API 读写。UI 能显示什么，取决于 API 给什么 |
| **没有鼠标的可靠支持** | 终端鼠标会与"拖选复制"冲突，行为不一致。当前**完全不用鼠标** |

## 三、布局（信息架构）

**固定高度，整屏，不滚动。** 纵向四个分区：

```
┌────────────────────────────────────────────────────────────┐
│ dsht  <会话标题>                    PgUp/PgDn 翻页 · ...    │ ← ① 标题栏（1 行）
├────────────────────────────────────────────────────────────┤
│ ↑ 上方 888 行                                              │
│                                                            │
│ > 你说的第一句话                                            │ ← ② 滚动区
│                                                            │   （对话记录，
│ = 智能体的回复                                              │     或面板的
│                                                            │     长文本）
│ ● 工具 read  report.md                                     │
│ ∗ 思考 先看目录结构，再挑重点章节读…                                │
│                                                            │
├────────────────────────────────────────────────────────────┤
│ ╭────────────────────────────────────────────────────────╮ │
│ │ > 在这里打字                                            │ │ ← ③ 下半区
│ ╰────────────────────────────────────────────────────────╯ │   （输入框
├────────────────────────────────────────────────────────────┤     或面板）
│ 173 轮 · 2260 步 · 208 tok/s · 缓存 99.5%         ○ 空闲    │ ← ④ 状态行（1 行）
└────────────────────────────────────────────────────────────┘
```

### 关键设计决定

1. **③ 下半区会在两种东西之间切换**：平时是**输入框**；当后端要你审批/回答时，**面板顶替输入框**（不是浮层盖住）。
   - 理由：终端里做浮层很容易乱；顶替最简单、最不容易出错。
   - 副作用：面板出现时看不到输入框（但你本来也不该在此时打字）。

2. **② 滚动区也会切换**：平时是对话记录；当面板需要你读一大段内容（比如"计划全文"）时，**改成显示那段全文**（这样可以用 PgUp/PgDn 翻阅）。

3. **底部没有留白**：整屏用满。（早期版本底部留了一行空白，用户提出"要么利用起来要么删掉"，已改。）

4. **盒子的高度必须等于它实际渲染的行数** —— 这条是本界面最容易出、最难查的 bug，
   所以单独列出来。

   **Ink 的 `overflow="hidden"` 不是裁剪，是挤压。** 固定高度的盒子装不下时，
   它会丢行、或者把两行文字叠在一起 —— 而且**总行数看起来还是对的**
   （实测：高度 5 的盒子装 6 行，输出仍是 5 行，但第一行没了）。
   表现出来只是「有点歪」，几乎不可能一眼定位。

   所以有两条硬规矩：

   - **谁产生内容，谁负责算它占几行。** `composerHeight()`（输入框，含边框和
     「上面还有 N 行」）、`panelHeight()`（面板）、`scrollLayout()`（滚动区里
     提示行和内容行互相抢位置）各自说清楚自己占多少行，`App` 只做加法。
     **不许在别处重算** —— 尤其不许写 `columns - 6`、`lines + 2` 这种魔法数，
     改了边框样式或内边距就会对不上。
   - **会换行的东西要么按真实折行数记账，要么主动裁成固定行数。** 错误消息来自服务端、
     长度不可控，所以折行后按行数算并封顶；标题可能是几十个汉字，所以按**显示宽度**裁剪。

   这条由 `tests/frame.test.tsx` 守着：它渲染**真实的 `App`**，断言帧行数正好等于终端行数，
   并且检查关键的行（比如「↑ 上面还有 N 行」）确实**完整**出现、没被别的文字压进来。
   只数总行数是不够的 —— 挤压发生时总行数往往仍然正确。

5. **空行规则：块之间空一行，块内部不空。**

   「块」有三种，正好对应三种角色：

   | 块 | 内容 |
   |---|---|
   | 用户块 | 一条用户消息 |
   | 系统块 | 一条命令反馈 / 错误提示 |
   | 智能体块 | 一段连续输出：思考 + 工具 + **回答** |
   | （系统块内部） | **命令本身 + 它的输出算同一个块**，中间不空行 |

   实际形态（用户亲自画的）：

   ```
   用户  kjsdbwklbfcw
         kjbfqbq
                              ← 空
   系统  askjdbwqkfqqw
                              ← 空
   思考  kjabdqdqd
   工具  nscbwfwqe
   回答  nkjbflwfvqwef
         kajdcbkjqbdkbqd
                              ← 空
   用户  cjbwqbdjqwbdqwd
                              ← 空
   思考  kjabfcwqfcq
   回答  njkasnfweqfqf
   ```

   **为什么块内部不空**：思考/工具/回答本来就是同一轮里连着发生的事，
   命令和它的输出更是同一件事的因和果。
   每条之间都插空行，会把一轮对话摊成三四段 —— 又占地方，又看不出它们是一伙的。

   用户实测发现的例子（命令被空行切成了两块）：
   ```
   - /permission workspace-write
                                 ← 这行空行是多余的
   - preset workspace-write
   ```

   规则实现在 `layout.ts` 的 `startsNewBlock()`：
   - 命令本身（`command/run`）→ **新块**（代表「又跑了一条命令」）
   - 命令的输出（`command/done`）/ 错误 → **接在命令后面**，不空行

   （早期做法是「除第一行外，每行前面都空一行」，空行多到把屏幕占满。
   用户和外部评审都指出过，改成现在这样。规则实现在 `layout.ts` 的
   `startsNewBlock()`，由 `tests/layout.test.ts` 锁住。）

6. **面板比屏幕长时必须裁，并且说清楚还有多少。**

   选项多、每个还带说明时，面板会长过一屏。**不裁的话 Ink 会挤压固定高度的盒子** ——
   丢行、两行文字叠在一起，连标题栏都被顶掉，而键盘**还能选到屏幕外的项**。

   最阴的是：这种情况下**帧行数往往仍然正确**，所以「只断言总行数」的测试会全绿。
   我们的测试就绿过一次 —— 实测 24 行终端上 40 个选项只剩 6 个可见、文字互相叠、
   标题栏消失，而那条断言依然通过。（外部评审抓出来的。）

   现在的规则：
   - 面板正文最多占**终端高度的一半**（`windowPanel`）
   - 装不下时显示 `… 还有 上面 N 行、下面 M 行（↑↓ 继续）`
   - **当前选中项永远可见**（窗口跟着光标滑）
   - `tests/frame.test.tsx` 同时断言：帧行数、标题栏/状态行/面板标题还在、
     装得下时选项一个不少、装不下时选中项可见且有提示、没有重复渲染的选项

7. **计划全文会自动跳到开头。** 滚动量 0 = 贴底，所以「显示全文」模式一进来就
   显式跳到顶部（给 state 塞一个很大的数，由 `scrollLayout` 夹紧）——
   计划是给人从头读的，不该先看结尾。面板里那句提示也说「可**用** PgUp/PgDn 翻阅」，
   而不是「按 PgUp 去翻」（那会让人以为得先按键才看得到开头）。

8. **两种"面板"，位置不一样，这是故意的。**

   | | 位置 | 为什么 |
   |---|---|---|
   | 事件面板（审批/提问/计划评审） | **顶替**输入框 | 它要独占键盘，此时你不该打字 |
   | 命令面板 | **叠在**输入框上方 | 你正是在输入框里敲 `/` 才叫出它的，藏起来就没法接着打字 |

## 四、视觉语言

### 4.1 颜色：语义令牌（两层结构）

架构借鉴了 Google Gemini CLI（Apache-2.0）：**调色板 → 语义令牌 → 组件**，组件里不出现具体颜色名。

但**令牌的划分方式不同**，而且这点是用户提出的：

> **它的令牌按「文字重要性」分**（primary / secondary / comment）。
> 那是因为在它的界面里，用户输入在底部独立输入框、不在滚动区，所以不需要用颜色区分"谁说的"。
> **我们的界面把用户和智能体放在同一条滚动记录里**，那"谁说的"就是最重要的信息。
> **所以令牌按「对象」划分。**

**一共 9 个令牌**（`src/ui/theme.ts` 是唯一真源，这张表必须跟它一致）：

| 令牌 | 深色底 | 浅色底 | 含义 |
|---|---|---|---|
| `user` | cyan | blue | 你说的话（整条） |
| `agent` | white | black | 智能体说的话（整条） |
| `tool` | green | green | 「● 工具」这个标签 |
| `thinking` | blueBright | blue | 「∗ 思考」这个标签 |
| `command` | blueBright | blue | 斜杠命令本身（如 `/plan off`） |
| `error` | redBright | red | 错误 |
| `dim` | gray | gray | 正文细节 / 提示（**退灰**） |
| `border` | gray | gray | 普通边框 |
| `attention` | yellow | red | **事件面板** · 等你回应 · 选中项 |

**三个令牌**在深色底上用了亮色档，理由都一样 ——「内容必须看清，而普通档对比度不达标」：

| 令牌 | 普通档 | 亮档 | 为什么破例 |
|---|---|---|---|
| `thinking` | blue 2.38:1 ❌ | blueBright **4.95:1** ✓ | 用户亲自挑的 DeepSeek 品牌蓝；普通蓝在深色底上几乎看不见 |
| `command` | blue 2.38:1 ❌ | blueBright **4.95:1** ✓ | 同上（代价：跟 `thinking` 撞色，靠标记区分） |
| `error` | red 3.23:1 ★★ 勉强 | redBright **5.09:1** ✓ | 错误是**必须看清**的东西，3.23:1 本来是全表最低的正文对比度之一 |

> **浅色底为什么不用亮档**：白底上「越亮越糊」，方向正好相反。
> 所以浅色主题一律挑深档 —— 这也是为什么同一件事在两个主题下选的档位不同。

**`attention` 这个令牌的设计意图**：它平时**用不到**，存在的意义就是"**突然跳出来**"——一旦出现，说明**后端在等你动手**。

（浅色底的完整映射见上面那张表 —— 早先这里只列了 5 个，漏掉了
`command` / `error` / `dim` / `border`。整表写在同一个地方，别在这里再列一遍。）

> 配色实测对比度见 `npm run contrast`（按 Windows Terminal 默认主题 Campbell 算）。
> 实测值（2026-09-14，深色底 `#0C0C0C`）：
> `agent/white` 12.18:1 · `attention/yellow` 7.47:1 · `user/cyan` 6.14:1 · `tool/green` 5.71:1
> · `error/redBright` 5.09:1 · `thinking`、`command`/blueBright 4.95:1 · `dim/gray` 4.31:1
> · `border/gray` 4.31:1 · `error/red`（未采用）3.23:1 · `blue`（未采用）2.38:1
>
> 这张表也会过期 —— 改配色时**跑一遍 `npm run contrast` 再回来改**，别凭记忆写。

### 4.2 行标记与「标签上色、内容退灰」

每一行的开头有一个标记符号，**都在第 0 列，不缩进**：

| 标记 | 码点 | 含义 |
|---|---|---|
| `> ` | U+003E | 你说的话 |
| `= ` | U+003D | 智能体说的话 |
| `● ` | U+25CF | 工具调用 |
| `∗ ` | U+2217 | 思考过程 |
| `- ` | U+002D | 系统消息（如命令反馈） |
| `! ` | U+0021 | 错误 |

### 一条硬规则：标记必须是「宽度确定」的字符

Unicode 把一批符号的东亚宽度**故意留白**（EAW=A），让字体决定 1 列还是 2 列。
我们用到的字符里，`●`（U+25CF，工具）就是这一类 —— 它是**用户亲眼确认过**
在自己终端里是 1 列，才被破例允许的。

被这条规则否掉的候选：`※`（U+203B 米印）、`≡`（U+2261 三条横线）、
`Ξ`（U+039E 希腊 Xi）、`◆`（U+25C6 实心菱形）。它们看起来都能用，
但只要换个终端或字体就可能变 2 列，整行左边缘参差 —— 而且**测试会全绿**，
因为我们的宽度算法只能按 1 列猜。`npm run markers` 末尾的尺子就是用来亲眼验证的。

面板里「当前选中哪一项」的标记**故意复用 `>`**（用户要求「跟①一致」）——
两个地方的意思都是「**你**在这」。它在面板里是黄色、缩进在方框内，
跟对话流里青色、顶格的用户行不会混。代码上 `PANEL_CURSOR_MARK`
直接由 `USER_MARK` 推出，所以你改了用户标记，面板自动跟着变。

> ⚠️ 这套标记是用户逐个挑出来的，**候选清单和宽度自检见 `npm run markers`**
> （自动生成的副本在 `docs/MARKERS.md`）。想换标记只改 `src/ui/layout.ts`。
>
> 已知风险：这套里唯一的**不定宽**字符是工具用的 `●`（U+25CF）。
> 它在用户机器上实测是 1 列；但如果换到「把不定宽字符渲染成 2 列」的终端/字体，
> 它会比其余五个标记宽 —— `npm run markers` 末尾的尺子就是核对这个的，
> `npm test` 也会直接报出来（`tests/markers.test.ts` 断言六个标记宽度一致）。
> 真遇到了就把 `●` 换成宽度确定的符号，候选表在 `npm run markers`。

**核心设计原则（用户提出，取代了我原来的方案）：**

> **颜色只用来标识「这是什么」，不用来铺满内容。**

具体表现：

- **工具行**：`● 工具 <工具名>` 是**绿色**的，只有后面的**参数**是**灰色**的。
  ```
  ● 工具 read  {"file_path":"report.md"}
  └绿色┘ └────────── 灰色 ──────────┘
  ```
- **思考行**：只有 `∗ 思考` 是**蓝色**的，后面的内容灰色。
- **用户/智能体**：这两者整条上色（因为它们是**主体内容**，且"谁说的"是最重要的信息）。
- **工具行强制压成一行**（超长截断加 `…`）。理由：工具参数经常是几百字符的命令，自由换行会把对话流淹没。需要看完整内容时……**目前哪里都看不全**（面板不显示参数，这是已知缺口，见第九节第 4 条）。

### 4.2.1 折叠的思考显示什么

**显示第一行 + 省略号**（有下文时才加），而不是一句「已折叠（Ctrl+O 展开）」。

```
∗ 思考 用户要结论。先看目录结构，再挑重点章节读，最后用三点总结。
      ↑ 折叠态就显示这一行（超宽会被截断）
```

改这一条的两个理由（用户指出）：

1. **原来那句话每个思考块后面都跟一遍**，很冗余 —— 而且它什么信息都不给，
   占一行只为了告诉你「这里有东西但我不给你看」。
2. **展开的快捷键已经写在标题栏的按键提示里了**，不需要每行再重复一次。

现在这样既省地方又有信息：一眼能看到它刚才在想什么。
真的要多看，按 `Ctrl+O` 展开全文。

> 边界：只有「还有下文」时才加省略号 —— 单行思考加省略号会让人以为被截断了。
> 首行本身超宽时按显示宽度裁剪，裁了也加省略号。

### 4.3 层级：靠「标记 + 颜色 + 空行」三者配合，**不靠亮度**

> ⚠️ 这一节以前叫「层级：用亮度排优先级」，还解释说「思考的 blue（2.4:1）偏暗是故意的」——
> 那是早期方案的残留，而且**跟 10.1 第 1 条说的正好相反**（那条说颜色只标识"是什么"、
> 不表示"有多重要"）。数据也早就过期了。外部评审指出后重写。

深色底上的实测对比度：

```
agent      white       12.18:1   ← 主体内容：你说的和它说的
attention  yellow       7.47:1   ← 只有"该你动手了"才出现
user       cyan         6.14:1   ← 你的话（整条上色，短，是锚点）
tool       green        5.71:1   ← 「● 工具」标签
error      redBright    5.09:1   ← 错误
thinking   blueBright   4.95:1   ← 「∗ 思考」标签
command    blueBright   4.95:1   ← 斜杠命令本身
dim/border gray         4.31:1   ← 所有"不是主角"的东西
```

**这些数字不构成层级**。高低差是"碰巧"，不是设计：`attention` 比 `user` 亮，
但"等你回应"并不比"你说的话"更重要 —— 它只是**更紧急**。

那层级靠什么表达？

| 手段 | 表达什么 |
|---|---|
| **标记符号** | 这是什么（`>` 你 / `=` 它 / `●` 工具 / `∗` 思考 / `-` 系统 / `!` 错误） |
| **颜色** | 同上，是标记的冗余编码（无色时靠符号，有色时更快） |
| **空行** | 块的边界（哪几行属于同一轮，见三.5） |
| **亮度（dim）** | 只有一个用途：**把"不是主角"的东西退到背景里**。工具参数、提示、折叠说明都用它 |

换句话说：**只有两档 —— 上色的，和退灰的**。上色的每个颜色只回答"这是什么"，
彼此之间没有高低之分。

## 五、状态

### 5.1 标题栏（1 行）

```
 dsht  会话标题                                    按键提示
```

左边是身份（徽标 + 标题，标题按**显示宽度**裁剪），右边是**按键提示**。

按键提示原来在状态行，现在搬到了这里 —— 因为状态行要给数据让位（见下）。
提示从长到短排，按宽度挑第一条放得下的：终端一窄，先牺牲「学会了就不用再看」的那些
（翻页、思考），最后只留「Enter 发送」。

`Esc` 的双重含义也在这里体现：**agent 在跑时**提示是 `Esc 停止 · Enter 插话 …`，
空闲时是 `Enter 发送 · …`。同一个键在不同状态下干不同的事，提示跟着变。

### 5.2 状态行（1 行）

```
 173 轮 · 2260 步 · 208 tok/s · 825M tok · 缓存 99.5% · 花费 6.34      ○ 空闲
```

右边是**状态词**（`○ 空闲` / `● 工作中` / `● 等你回应`），左边是**这个会话的实际数据**。

数据全部来自 dsh 自己算好的**会话投影**（`session.projections.faceOf(key)`），
我们不自己统计、更不估算：

| 显示 | 来源 | 怎么算 |
|---|---|---|
| `173 轮` | `sessionStats.turns` | 原值 |
| `2260 步` | `sessionStats.steps` | 原值 |
| `208 tok/s` | `sessionStats` | `decodeTokens / (decodeMs / 1000)` |
| `825M tok` | `tokenUsage.cacheReadTokens` | 原值（跟 dsh 的 Web UI 一致，它显示的就是缓存读取量） |
| `缓存 99.5%` | `tokenUsage` | `cacheRead / (cacheRead + uncachedInput)` —— 分母**只算输入**，输出 token 不参与缓存 |
| `花费 6.34` | `costUsage.cost` | 原值，计价单位由 dsh 决定，我们**不换算** |
| `上下文 65%` | `contextPressure` | `projectedTokens / contextWindow` |

**两条硬规矩**：

1. **取不到就整段省掉，绝不编。** 缺的键就是 `undefined`，那一项直接不显示。
   用户对花费敏感，编一个数字出来只会让他更焦虑。
2. **按宽度降级。** 候选文案从长到短排，第一段（轮次）永远留着。
   顺序反映了重要性：轮次 > 速度 > 总量 > 命中率 > 花费 > 上下文。
   `0 tok` 这种噪音会被过滤掉（新会话不该显示它）。

| 键 | 作用 |
|---|---|

| `Esc` | 拒绝 |
| `Y` / `N` | 直接允许一次 / 直接拒绝 |

### 6.6 提问面板

| 键 | 作用 |
|---|---|
| `↑` `↓` | 选择选项（含末尾的「自行输入…」） |

### 6.7 事件面板的优先级

**事件面板（审批 / 提问）> 命令面板 > 输入框。** 审批一来就把命令面板收掉 ——
键盘归属永远只有一个，不会出现多个处理器抢事件。

## 六之二、文案规范

用户的要求原话：「各种提示类的信息，表述要**统一、简洁、严谨、书面**，不要那种口语化的表达。
一定要统一，这样符合审美。」

### 规则

1. **统一的分隔符**：提示里的条目一律用 ` · ` 分隔（前后各一个空格）。
2. **统一的方向词**：用「**上方 / 下方**」，不用「上面 / 下面」。箭头负责表意，文字只需对称。
3. **统一的动作词**：`选择` / `确认` / `取消` / `返回` / `翻阅` / `输入`。不用「敲」「按一下」「点」。
4. **不重复**：同一条提示不在多处重复。比如「Ctrl+O 展开思考」只写在标题栏的按键提示里，
   不再每一行思考后面都跟一句 —— 那样既冗余又像噪音（用户指出）。
5. **不用口语**：`说点什么吧` → `尚无对话`；`菜单还没做（下一步）` → `菜单尚未实现`；
   `不认识的命令` → `无法识别的命令`。
6. **键名保持原样不翻译**：`Enter` / `Esc` / `Tab` / `PgUp` / `Space` 里的 `Space` 是例外 ——
   键盘上印的是空格，所以写「**空格**」而不是 `Space`。
7. **能省就省**：`（计划全文见上方 · PgUp/PgDn 翻阅）` —— 用 `·` 而不是「，可用……翻阅」。

### 现状对照（改过的）

| 改前（口语 / 不统一） | 改后 |
|---|---|
| `（还没有对话，说点什么吧）` | `（尚无对话）` |
| `↑ 上面 12 行 · ↓ 下面 8 行` | `↑ 上方 12 行 · ↓ 下方 8 行` |
| `↑ 上面还有更早的记录 · 按 PgUp 载入` | `↑ 尚有更早记录 · PgUp 载入` |
| `↑ 已经是最早的记录` | `↑ 已是最早记录` |
| `↑ 正在载入更早的记录…` | `↑ 正在载入更早记录…` |
| `自己输入…` | `自行输入…` |
| `↑↓ 选择 · Space 勾选 · Enter 确认 · 直接打字可补充` | `↑↓ 选择 · 空格 勾选 · Enter 确认 · 打字可补充` |
| `↑↓ 选择 · Enter 确认 · 直接打字可自己回答` | `↑↓ 选择 · Enter 确认 · 打字可自行回答` |
| `Enter 提交 · Esc 返回选项` | `Enter 提交 · Esc 返回` |
| `这条命令的参数没法变成选项` / `需要自己写：` | `此命令的参数无法转为选项` / `需手动输入：` |
| `不认识的命令：/x（没有发给模型）` | `无法识别的命令：/x（未发送）` |
| `Esc 菜单还没做（下一步）` | `Esc 菜单尚未实现` |
| `没有匹配的命令` | `无匹配命令` |
| `（计划全文见上方，可用 PgUp/PgDn 翻阅）` | `（计划全文见上方 · PgUp/PgDn 翻阅）` |

## 八、已知的取舍（有意的，不一定最优）

| 取舍 | 选择 | 代价 |
|---|---|---|
| 面板出现的方式 | 事件面板顶替输入框，命令面板叠在输入框上方 | 两种"面板"位置不同，需要解释（见三.6） |
| 工具行 | 强制单行截断，只显示**调用**不显示**结果** | 看不到工具干了什么、看到什么（没有全局展开手段） |
| 长面板 | 超出终端高度一半就裁掉，只显示光标周围 | 一次看不全所有选项，要靠 ↑↓ 翻 |
| 英文折行 | 优先在词边界断 | 行尾可能短一截（比把词劈开强） |
| 思考 | 默认折叠，只显示**首行 + 省略号** | 想看全文要按 Ctrl+O |
| 空行 | 只在块之间留 | 块内部靠标记和颜色区分，无色环境下会糊成一片 |
| 颜色 | 只用 16 基础色 | 无法精确控制观感，跟着用户主题走 |
| 颜色 | 语义令牌**按对象**分（user/agent/tool/thinking/command），不按"重要程度"分 | 无法用亮暗表达层级；且 `thinking`/`command` 会撞色（都是蓝） |
| 光标 | 用终端真光标（不是自绘） | 形状/颜色由终端决定，我们只能改形状 |
| 加粗 | **完全不用** | 少一个强调手段；换来的是观感可预测（终端会把 bold+基础色渲染成亮色版） |
| 鼠标 | 完全不用 | 不能用点击 |
| 命令 | 有面板可选，但仍能手打 | 两条路径都要维护 |

## 十、我（写这份文档的 AI）对这份设计的看法

### 10.1 我认为已经成立的，评审时请重点质疑而不是建议推翻

1. **颜色只标识「这是什么」，不表示「有多重要」。** 大多数 CLI 用颜色表达重要性（越重要越亮），
   结果是屏幕越花、越难扫。这里每个颜色绑定一个**对象**（你/它/工具/思考/命令），
   正文一律退灰。这条撑住了整个视觉语言。
2. **标记固定在第 0 列，正文从第 2 列开始。** 左边缘是一条稳定的扫描轨，
   不管内容怎么换行、怎么折行都不动。
3. **两种面板，位置不同。** 事件面板要独占键盘所以顶替输入框；命令面板是在输入框里叫出来的，
   所以叠在上面、输入框留在底部。这个区分是有理由的，不是随手定的。
4. **高度账由「产生内容的那个盒子」负责。** Ink 的 `overflow` 是挤压不是裁剪，
   分散在几处手算必然出错（已经出过一次：提示行没进预算，首行被压花）。
5. **预览和文档都调用真代码。** 所有截图/示例都是跑真组件渲染出来的，不存在"文档说的和实际不一样"。

### 10.2 我心里没底的三件事

1. **空行收紧之后，「块」的边界还够清楚吗？**
   现在全靠每行开头 2 列的标记 + 颜色区分角色。有颜色时够用，
   但**去掉颜色**（截图、黑白打印、不支持颜色的终端）会不会糊成一片？
   这是我最想听评审意见的一条。

2. **状态行的降级顺序合不合理、模型名该不该挤进来。**
   状态行已经是投影数据了（轮次/步数/速度/缓存/花费），按键提示搬到了标题栏。
   还剩一个问题：`modelSelection` 投影里有当前模型，但一行放不下 —— 该牺牲谁？

3. **工具结果的呈现。** 「调用可见、结果不可见」是不是个错误？还是说
   让 agent 用自然语言总结就够（它本来就会总结）？我不知道哪种对用户更好。

### 10.3 我想提的具体改动（等评审者点头再做）

1. ~~状态行加成本信息~~ —— **已完成**（`costUsage` 投影 → 状态行的「花费」一项）。

2. **工具行加一行结果摘要。** 形态：`● 工具 read  report.md  → 3.2 KB`（仍然单行）。
   现在还只显示调用参数。展开时看全文（像思考那样 Ctrl+O）。

3. **命令面板第二步：枚举型参数变成子面板。**
   `/permission` 的三个预设、`/plan off` 的 off，都应该是可选项而不是要手打的字符串。
   技术障碍：`commands/list` 只给了 `input.hint`（形如 `<preset>`），**没给枚举值**。
   要么请上游在协议里暴露，要么我们维护一份已知枚举 —— 后者会漂移，不推荐。

4. **往上翻时的"新消息"提示。** 新回复到达时**不要**打断阅读、不要自动跳到底，
   只在状态行显示 `↓ 3 条新消息（End 跳到最新）`。

### 10.4 一个我一直没解决的长期问题

`src/ui/App.tsx` 现在是 700 多行，同时管布局、状态、键盘路由、光标测量、发送逻辑。
按"状态所有权"该拉出来的缝已经想清楚了（键盘路由 / 会话订阅 / 交互队列 / 编辑器 / 光标锚点），
但**每一轮加功能都会让这个文件更大**。这是一个会持续恶化的结构问题，
只不过它现在还没到妨碍改动的程度 —— 所以一直没优先做。

## 附：怎么看实际效果

项目里有一个预览脚本，会渲染出**和真实界面一致**的样例：

```sh
npm run preview:ui                    # 三种面板一次看清（事件面板 / 命令面板 / 计划全文整屏）
npm run palette:preview               # 完整界面（配色视角），深色底
DSHT_THEME=light npm run palette:preview   # 浅色底
npm run markers                       # 行首标记的候选清单 + 宽度自检尺子
npm run contrast                      # 配色对比度实测
npm run symbols                       # 符号候选图表（码点、宽度）
npm run palette:chart                 # 16 个基础色色卡
```

> 这些脚本都调用**真实的**组件和函数渲染，不是手画的示意图 ——
> 所以文档里的示例和实际运行一定一致。这也是为什么这份文档可以放心照着评。

技术栈：TypeScript + [Ink](https://github.com/vadimdemedes/ink)（React 写终端 UI）+ Node。
